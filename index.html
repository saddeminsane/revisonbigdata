1 — Big Data, NoSQL et pourquoi le modèle classique pose problème

Big Data : définition du cours

Le Big Data concerne la gestion et l'analyse de données massives. Le point important du support est que les besoins de stockage et/ou de traitement peuvent dépasser très largement les capacités d'une seule machine.

Conséquence : on utilise des plateformes distribuées capables de stocker et traiter les données sur plusieurs serveurs : Hadoop, Spark, TensorFlow, MongoDB, Kafka, etc.

NoSQL = « Not Only SQL »

Les bases NoSQL sont une famille de bases non relationnelles conçues notamment pour gérer de grandes quantités de données non structurées ou semi-structurées.

  • Scalabilité horizontale importante.
  • Données pouvant être distribuées sur plusieurs serveurs.
  • Modèles de données plus flexibles que le schéma relationnel classique.
  • Objectif général : faciliter la gestion de données massives et distribuées.
Famille NoSQLPrincipeExemples du cours
DocumentsDocuments JSON/BSONMongoDB, CouchDB
Clé-valeurPaires clé → valeurRedis, Amazon DynamoDB
ColonnesDonnées organisées par colonnesCassandra, HBase
GraphesRelations représentées comme un grapheNeo4j, ArangoDB
À mémoriser : MongoDB = NoSQL orienté documents, avec représentation JSON/BSON.

2 — Bases relationnelles, transactions et distribution

Transaction

Une transaction est une séquence d'opérations de lecture/écriture qui doit être exécutée entièrement ou pas du tout.

Exemples : virement bancaire, validation d'un panier d'achat.

BEGIN / startTransaction()→ opérations→ COMMIT

En cas d'échec : ROLLBACK / annulation.

ACID

LettreSignificationIdée à retenir
A — AtomicitéTout ou rienUne transaction réalise toutes ses actions ou aucune.
C — CohérenceIntégritéLes règles d'intégrité doivent être respectées.
I — IsolationPas d'interférenceLes modifications d'une transaction ne sont pas visibles aux autres avant validation.
D — DurabilitéPersistanceUne modification validée doit survivre à une panne.
Piège DS : ne pas confondre cohérence ACID et « cohérence à terme » d'un système distribué. Ce sont deux contextes différents.

Transaction distribuée

Une transaction est distribuée lorsque ses opérations ont lieu sur plusieurs sites/serveurs distants. Exemple du support : virement d'une banque A vers une banque B.

Le problème essentiel : garantir l'atomicité malgré la distribution. Si une opération échoue, il faut éviter que l'autre soit définitivement validée.

2 Phase Commit — 2PC

Le protocole Two-Phase Commit utilise un coordinateur et plusieurs participants.

Phase 1 — Vote

  1. Le coordinateur envoie les opérations aux participants.
  2. Chaque participant exécute ses opérations.
  3. Chaque participant répond Oui/Non.

Phase 2 — Décision

  • Tout le monde répond Oui : le coordinateur envoie COMMIT.
  • Au moins un Non : le coordinateur envoie ROLLBACK.
Problème à grande échelle : les pannes fréquentes peuvent provoquer des annulations et une forte lenteur. C'est l'une des motivations derrière les architectures NoSQL distribuées.

Jointures et scalabilité

Dans le relationnel, les informations sont souvent réparties sur plusieurs tables. Pour reconstruire une entité complexe, on utilise des jointures.

À grande échelle, les jointures et les écritures distribuées peuvent devenir coûteuses. Le modèle documentaire cherche donc à regrouper les données liées dans des documents autonomes afin de minimiser les jointures.

3 — Modèle orienté document

Modèle agrégé de données

Un document peut regrouper les informations qui appartiennent logiquement à une même entité. Exemple du support : un film contenant son réalisateur et une liste d'acteurs.

{
  "id": 1,
  "title": "Dachra",
  "year": 2018,
  "genre": "Horror",
  "director": {
    "id": 1,
    "last_name": "Bouchnak",
    "first_name": "Abdelhamid",
    "birth_year": 1984
  },
  "actors": [
    {
      "id": 8,
      "last_name": "Jebali",
      "first_name": "Aziz",
      "birth_year": 1986,
      "role": "Walid"
    }
  ]
}

Pourquoi ce modèle ?

  • Les données liées sont regroupées.
  • On évite certaines jointures.
  • On réduit certaines écritures distribuées.
  • Le modèle est adapté aux données semi-structurées.
  • La structure peut être imbriquée.

Inconvénients du modèle agrégé

  • Redondance : la même information peut être copiée dans plusieurs documents.
  • Risque d'incohérence : une copie peut être modifiée sans que les autres le soient.
  • Mises à jour difficiles : toutes les copies doivent être maintenues.
  • Certains accès deviennent moins efficaces : certaines recherches complexes peuvent nécessiter plusieurs requêtes.
  • Entités indépendantes : une entité comme un acteur peut être difficile à gérer séparément si elle est encapsulée dans un document film.
Avantage central du support : éviter les jointures et les écritures distribuées.

Relationnel vs document

RelationnelOrienté document
Tables, lignes, colonnesDocuments JSON/BSON
Schéma fixeStructure flexible
Jointures fréquentesRegroupement des données liées
Très adapté aux relations complexesTrès adapté aux données semi-structurées et applications modernes
Distribution plus délicate lorsque les données sont fortement liéesAutonomie des documents facilitant la distribution
Notion importante : autonomie. Plus les documents sont autonomes, plus il est facile de les distribuer. Si les données dépendent fortement les unes des autres, les jointures réapparaissent et les avantages du NoSQL diminuent.

MongoDB est un système NoSQL orienté documents. Le support le présente comme un système semi-structuré, basé sur une représentation JSON, avec une grande flexibilité de schéma et conçu dès l'origine pour être scalable et distribué.

5 — Requêtes MongoDB

Idée générale

MongoDB permet d'exprimer l'équivalent de nombreuses recherches SELECT ... FROM ... WHERE ... sur une collection, sans jointure classique dans les requêtes simples.

Recherche par clé

db.artists.find({
  _id: "artist:99"
})

Recherche dans un chemin imbriqué

db.movies.find({
  "director.last_name": "Scott"
})

Le même principe peut être utilisé dans un tableau d'objets :

db.movies.find({
  "actors.last_name": "Weaver"
})

findOne, pagination et projection

db.movies.findOne({
  "actors._id": "artist:99"
})

db.movies.find({
  "actors._id": "artist:99"
}).skip(0).limit(2)

db.movies.find(
  {"actors._id": "artist:99"},
  {"title": 1}
)
  • findOne() : récupérer un document correspondant.
  • skip(n) : ignorer les premiers résultats.
  • limit(n) : limiter le nombre de résultats.
  • Projection : choisir les champs retournés.

Expressions régulières

db.movies.find(
  {"title": /^Re/},
  {"title": 1}
)

Ici, le titre doit commencer par Re.

Recherche par intervalle

db.movies.find({
  "year": {
    $gte: 2000,
    $lte: 2005
  }
})

$gte = greater than or equal ; $lte = less than or equal.

Opérateurs ensemblistes

db.artists.find({
  _id: {
    $in: ["artist:34", "artist:98", "artist:1"]
  }
})

Le support cite notamment $in, $nin, $all et $exists.

db.movies.find({
  summary: {$exists: true}
})

Opérateurs booléens

Quand plusieurs critères sont placés dans une même expression de recherche, le comportement présenté est une conjonction logique par défaut.

db.movies.find({
  $and: [
    {"year": "1997"},
    {"actors.last_name": "DiCaprio"}
  ]
})

db.movies.find({
  $or: [
    {"year": "1997"},
    {"actors.last_name": "DiCaprio"}
  ]
})
À savoir expliquer : les requêtes MongoDB ont une expressivité comparable à SQL pour les recherches à l'intérieur d'une même collection, mais la logique de modélisation est différente. Lorsque les informations sont réparties entre collections, on peut utiliser l'Aggregation Pipeline et notamment $lookup.

Mise à jour / suppression

db.test.update(
  {"_id": "movie:2"},
  {$set: {sous_titre: "Le passager"}}
)

db.test.update(
  {"_id": "movie:2"},
  {$unset: {country: 1}}
)

db.test.remove()

$set ajoute/modifie un champ ; $unset supprime un champ. La dernière commande illustrée dans le support supprime les documents correspondant à l'opération.

6 — Aggregation Pipeline

L'Aggregation Pipeline est une succession d'étapes/opérateurs permettant d'effectuer des traitements plus complexes que les recherches simples avec find().

Principe

Collection→ $match→ $group→ $sort→ $limit→ Résultat

Compter les films d'un genre

db.movies.aggregate([
  {$match: {genre: "drama"}},
  {$count: "nombreFilms"}
])

Les 3 réalisateurs ayant dirigé le plus de films

db.movies.aggregate([
  {$group: {
    _id: "$director._id",
    total: {$sum: 1}
  }},
  {$sort: {total: -1}},
  {$limit: 3}
])

Les 3 acteurs ayant joué dans le plus de films

db.movies.aggregate([
  {$unwind: "$actors"},
  {$group: {
    _id: "$actors._id",
    total: {$sum: 1}
  }},
  {$sort: {total: -1}},
  {$limit: 3}
])

$unwind est particulièrement important : il transforme les éléments d'un tableau en éléments séparés du pipeline, ce qui permet ensuite de les regrouper/comptabiliser.

$lookup : jointure dans l'Aggregation Pipeline

Le support indique que MongoDB possède depuis la version 3.2 l'opérateur de jointure $lookup.

db.moviesAvecRef.aggregate([
  {
    $lookup: {
      from: "artists",
      localField: "director._id",
      foreignField: "_id",
      as: "realisateur"
    }
  },
  {
    $project: {
      "title": 1,
      "realisateur.last_name": 1
    }
  }
])
OpérateurRôle
$matchFiltrer les documents
$groupRegrouper et calculer des agrégats
$sumSommer / compter avec $sum:1
$sortTrier
$limitLimiter le nombre de résultats
$unwindDécomposer un tableau
$lookupFaire une jointure entre collections
$projectChoisir/transformer les champs retournés

7 — MongoDB et ACID

Le support précise que MongoDB introduit le support des transactions ACID à partir de la version 4.0.

session = db.getMongo().startSession();
db = session.getDatabase("maBase");
collection = db.getCollection("maCollection");

session.startTransaction();

try {
  collection.insertOne({ name: "Document 1" });
  collection.insertOne({ name: "Document 2" });

  session.commitTransaction();
}
catch (error) {
  session.abortTransaction();
}
finally {
  session.endSession();
}

À retenir

  • Une session est démarrée.
  • Une transaction est démarrée avec startTransaction().
  • Les opérations sont exécutées.
  • En cas de succès : commitTransaction().
  • En cas d'erreur : abortTransaction().
  • La session est terminée avec endSession().
Différence avec le relationnel : dans le support, les transactions MongoDB ne sont pas présentées comme obligatoires pour toute opération, contrairement au modèle relationnel classique.

8 — Réplication : pourquoi et comment ?

Pourquoi répliquer ?

  • Tolérance aux pannes : si un serveur tombe, une copie existe ailleurs.
  • Distribution des lectures : plusieurs serveurs peuvent répondre aux lectures.
  • Disponibilité : le système continue à fonctionner malgré certaines pannes.
  • Possibilité d'effectuer certaines opérations sur une copie sans affecter directement les autres.
Idée simple : réplication = plusieurs copies des mêmes données.

Réplication synchrone vs asynchrone

SynchroneAsynchrone
Le serveur principal attend les confirmations des autres.Le serveur principal n'attend pas toutes les copies.
Plus forte cohérence.Plus rapide.
Plus de latence.Risque d'incohérence temporaire.
Le support : sécurité/cohérence fortes mais lenteur.Le support : sécurité partielle, cohérence faible, efficacité.

Journalisation

Le support rappelle l'utilisation d'un fichier journal pour éviter certaines latences disque et permettre de ramener les écritures vers des entrées/sorties séquentielles.

9 — Cohérence, failover et théorème CAP

Cohérence forte

À tout instant, il ne doit pas y avoir deux valeurs/versions différentes d'une même donnée. Une opération validée est permanente et immédiatement visible.

Cohérence faible

On accepte qu'une lecture puisse temporairement ne pas refléter la dernière mise à jour.

Cohérence à terme — Eventual Consistency

Le système accepte des incohérences transitoires mais garantit qu'elles finiront par disparaître : les copies convergent vers un même état.

Logique du cours : les systèmes NoSQL privilégient souvent la réplication asynchrone et les performances au détriment d'une cohérence forte immédiate.

Failover

Le failover est la reprise du service lorsqu'un serveur tombe en panne.

  • Les serveurs échangent des messages de type heartbeat.
  • Si un secondaire tombe, les autres peuvent continuer.
  • Si le maître tombe, les secondaires doivent élire un nouveau maître.
  • En cas de partition réseau, la majorité est essentielle pour éviter que plusieurs groupes élisent chacun leur propre maître.

Théorème CAP

Le support présente CAP comme une limitation intrinsèque aux systèmes distribués :

CConsistencyLes lectures voient une donnée cohérente.
AAvailabilityLe système continue à répondre.
PPartition toleranceLe système tolère une séparation du réseau en groupes.
À mémoriser : selon le support, un système distribué ne peut pas satisfaire simultanément les trois garanties dans le sens fort du théorème CAP ; il faut donc faire un compromis.

MongoDB : Replica Set

Un Replica Set est un ensemble de serveurs MongoDB partageant des répliques du même ensemble de documents.

  • Primary : un seul dans un replica set ; les écritures ont lieu sur lui.
  • Secondaries : récupèrent l'opLog et maintiennent une copie locale.
  • Arbiter : peut éventuellement participer à certaines fonctions d'élection.

opLog

Le opLog est le journal des opérations de modification. Le Primary enregistre les modifications et les Secondaries récupèrent ce journal pour mettre à jour leur copie.

MongoDB et niveaux de cohérence

Cohérence forteCohérence à terme
Le client lit toujours via le Primary.Le client peut lire un Secondary.
Les Secondaries ne servent pas à distribuer les lectures.Permet de répartir certaines lectures.
Les Secondaries servent principalement de réplication/secours.Choix possibles selon la latence ou le secondaire préféré.
Phrase DS : « La réplication améliore la tolérance aux pannes et peut distribuer les lectures, mais le partitionnement est le mécanisme privilégié pour augmenter la capacité à grande échelle. »

10 — Sharding : partitionner pour passer à l'échelle

Pourquoi partitionner ?

Le Big Data nécessite des capacités de stockage, CPU et RAM très importantes. Deux approches existent :

Scalabilité verticaleScalabilité horizontale
Augmenter la puissance d'une seule machine.Ajouter de nouvelles machines.
Limite physique et économique.Les données/calculs sont répartis sur un cluster.
Une machine très puissante peut coûter disproportionnellement cher.Augmente le débit et réduit la charge de chaque serveur.
Sharding = partitionnement horizontal des données. On découpe une grande collection en fragments distribués sur plusieurs serveurs.

Comment fonctionne le sharding ?

  1. Découper une grande collection en fragments appelés chunks.
  2. Le découpage se fait selon une shard key / clé de partitionnement.
  3. Distribuer les chunks sur différents serveurs appelés shards.
  4. Maintenir un répertoire indiquant quel chunk se trouve sur quel shard.
  5. Un routeur consulte ce répertoire et envoie la requête au bon shard.
Client→Routeur→Répertoire→Shard

Chunk

Un chunk est un fragment de données. Le support indique qu'il possède généralement une taille maximale prédéfinie, de l'ordre de dizaines de Mo à quelques Go selon le système. On retrouve des termes similaires dans d'autres systèmes : tablet, region, bucket, etc.

Structure d'un système partitionné

Le routeur n'a pas besoin de connaître chaque document individuellement : il utilise une structure de routage qui associe les fragments aux serveurs.

Pourquoi ne pas envoyer directement chaque requête à tous les serveurs ? Parce que cela provoquerait du travail inutile. Le routeur cherche à identifier le shard pertinent.

Équilibrage et élasticité

Un bon système de sharding doit assurer :

  • Load balancing : répartir équitablement la charge.
  • Élasticité : s'adapter à l'ajout/suppression de données et à l'ajout/disparition de serveurs.

Split et migration

OpérationRôle
SplitDiviser un chunk devenu trop gros.
MigrationDéplacer un chunk d'un shard vers un autre pour équilibrer la charge.

Le support précise que le split est relativement peu coûteux alors que la migration est coûteuse, car elle implique le déplacement des données. Le système effectue donc généralement une migration à la fois.

Tolérance aux pannes dans un système partitionné

  • Le répertoire de routage est critique : s'il constitue un SPOF, sa panne peut bloquer le système.
  • Le répertoire doit donc être répliqué.
  • Les fragments doivent eux aussi être répliqués.

11 — Le sharding de MongoDB — jusqu'à la diapositive 69

Architecture MongoDB sharded

Config Server

Stocke le répertoire / les métadonnées permettant de savoir où se trouvent les chunks.

Le support insiste sur le fait qu'il doit être répliqué.

mongos — Query Router

Reçoit les requêtes des clients, consulte les informations du Config Server, oriente les requêtes vers le ou les shards appropriés, agrège les résultats puis les renvoie au client.

Stateless : il ne stocke pas les données.

Shard

Serveur de données contenant une partie des données. Dans l'architecture présentée, chaque shard est un Replica Set complet.

Balancer

Processus d'arrière-plan chargé de contribuer à la répartition de la charge, notamment via la migration de chunks.

Schéma mental à mémoriser

Client→ mongos→ Config Server→ Shard approprié

Le mongos est le point d'entrée côté client. Le Config Server fournit les métadonnées de routage. Les shards stockent réellement les données.

Pourquoi plusieurs mongos ?

Le support précise qu'il peut y avoir plusieurs routeurs. Ils sont stateless. Un client envoie sa requête à un routeur, qui se charge du routage.

Ajouter des shards

La diapositive 69 présente un petit test de configuration.

# Config Server
mkdir /data/configdb
mongod --configsvr --dbpath /data/configdb --port 27019

# Si le Config Server est répliqué
mongod --configsvr --replSet nomRS --dbpath <path>

# Routeur
mongos --configdb localhost:27019

# Avec Config Server répliqué
mongos --configdb nomRS/confServer1:port1,confServer2:port2,confServer3:port3

# Deux serveurs de données pour le test
mongod --dbpath /data/node1 --port=30001
mongod --dbpath /data/node2 --port=30002

# Depuis mongos
sh.addShard("localhost:30001")
sh.addShard("localhost:30002")
sh.enableSharding("dbtp")
Attention DS : le support précise que, pour la production, il faudrait des Replica Sets complets pour les shards ; le test de la diapositive utilise une configuration simplifiée.

Fin exacte du périmètre

La diapositive 69 est la dernière diapositive à réviser. Elle termine la première partie pratique du sharding MongoDB avec le lancement du Config Server, du routeur, de deux serveurs, l'ajout des shards et l'activation du sharding de la base.

Ne pas réviser au-delà pour ce DS : le support passe ensuite à d'autres développements du partitionnement distribué / hachage et à Cassandra, mais ces parties sont hors du périmètre demandé.

Bloc D — Questions pièges avec réponses

Pourquoi le NoSQL réduit-il l'utilisation des jointures ?

Parce que le modèle documentaire regroupe les données liées dans des documents autonomes. On récupère donc une grande partie des informations dans un même document au lieu de reconstruire l'entité à partir de plusieurs tables.

Pourquoi la scalabilité verticale a-t-elle des limites ?

Les ressources d'une seule machine ne peuvent pas augmenter indéfiniment et les machines très performantes sont coûteuses. Le cloud fournit également souvent des instances de taille limitée.

Pourquoi la réplication asynchrone est-elle plus rapide ?

Parce que le serveur qui reçoit l'écriture n'attend pas la confirmation de toutes les copies avant de répondre au client. En contrepartie, une copie secondaire peut temporairement être en retard.

Pourquoi faut-il une majorité lors d'une élection ?

Pour éviter qu'une partition réseau permette à plusieurs groupes de considérer chacun qu'il est autorisé à élire son propre maître. La majorité permet de maintenir une décision unique.

Pourquoi choisir soigneusement la shard key ?

Parce qu'elle détermine comment les documents sont répartis et influence directement les performances, la distribution de charge et le routage des requêtes.

Quel est le rôle du mongos ?

Recevoir la requête, consulter les métadonnées nécessaires au routage, envoyer la requête au shard approprié, éventuellement récupérer plusieurs résultats, les agréger puis répondre au client.

Quel est le rôle du Config Server ?

Stocker les métadonnées / le répertoire indiquant où se trouvent les chunks et donc permettre au routeur de savoir où envoyer les requêtes.

Pourquoi les chunks sont-ils importants ?

Ils constituent les unités de découpage et de déplacement des données dans le système partitionné. Ils peuvent être splittés lorsqu'ils deviennent trop gros et migrés pour équilibrer la charge.

Mini-plan de mémorisation avant le DS

1. Apprendre les définitions : NoSQL, document, transaction, réplication, sharding.
2. Maîtriser ACID + 2PC + CAP.
3. Savoir expliquer Primary/Secondary/opLog/Replica Set.
4. Savoir expliquer le chemin Client → mongos → Config Server → Shard.
5. Réviser les commandes find, opérateurs, aggregate et commandes de sharding.
6. Faire les comparaisons : réplication vs sharding, vertical vs horizontal, synchrone vs asynchrone.
La logique globale du cours :
Big Data → une machine ne suffit plus → distribution → les transactions et jointures deviennent difficiles à grande échelle → NoSQL propose des modèles plus adaptés → MongoDB utilise des documents → la réplication améliore disponibilité/tolérance aux pannes → le sharding répartit les données pour passer à l'échelle → MongoDB combine Config Server + mongos + shards.
